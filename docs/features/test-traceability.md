## Scope, method, and evidence vocabulary

Current AST baseline: **82 feature IDs**, **47 invariant IDs**, **28 app test modules**, **414 app test methods**, and **2 `expectedFailure` methods**. SQLite is the fast lane; the required integration lane runs the complete suite against an ephemeral PostgreSQL 17 service. PostgreSQL-only tests use `TransactionTestCase`, separate connections, and barriers or events at exact race boundaries. No row treats a passing sub-contract as proof of an entire feature: evidence identities and each applicable dimension are reviewed separately.

Statuses: `C` executed coverage at the stated level; `XF` a focused expected-failure characterization; `M` missing; `D` explicitly deferred; `NA` not applicable. Dimensions are always individual: positive, negative, authorization, validation, idempotency, concurrency, external-I/O, mobile, theme, accessibility, configuration, migration, deployment, production. A source assertion is not executed JavaScript. `executed DOM/Chromium` runs the production script in a real browser engine against controlled HTML and fetch fakes, but is not a live Django/browser/SQLite flow; `real Playwright browser/SQLite` is that higher live-server level. A Compose render is not launched Compose, mocked outbound I/O is not a live provider, and a simulated inbound request is not provider delivery. The checker's allowed mechanism vocabulary is structural; its audited semantic expectation map guards selected critical records, while independent review remains responsible for the complete semantic truth of all 276 bodies.

`expectedFailure` means only that the decorated method raised an expected exception. Confidence that it raised for the intended defect comes from focused setup/assertions and review of the unwrapped test; the decorator alone does not establish cause. AST discovery recognizes bare `expectedFailure` and syntactically qualified `.expectedFailure`; it deliberately does not resolve imported aliases.

## Maintenance and review protocol

1. Update feature/invariant rows, every applicable dimension, exact ledger ownership, summary counts, and exact Witan slugs with every behavior or test change. Never alter snapshot pins/counts through this live matrix.
2. Primary evidence must be an exact primary ledger row mapped to that ID. Map only behavior asserted by the test body. Supporting fixture/source/markup guards do not become feature coverage unless the contract itself is static and the ledger/matrix both say so.
3. Treat `expectedFailure` as expected exception only. Review focused setup/assertions and run the method unwrapped when diagnosing cause. A fix removes the decorator and updates result/status/counts.
4. Keep external boundaries explicit: simulated inbound, mocked outbound, live provider, local DB, source Compose, rendered Compose, launched Compose, historical pinned observation, and current-HEAD observation are different levels.
5. Run the checker and its mutation tests before the app suite. The checker enforces stable IDs/pins, exact dimension grammar, ownership, mechanisms, sequential ledger numbers, C/XF decorators, counts, summaries, specialized task slugs, and top-level test discovery.

```bash
uv run python scripts/check_test_traceability.py
uv run python -m unittest tests.traceability_checker_cases
uv run python manage.py test feeds
```
